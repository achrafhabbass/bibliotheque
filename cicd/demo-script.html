Le contexte (à enchaîner)

Le développement logiciel moderne fait face à un paradoxe : plus un projet grandit, plus les tâches répétitives — compiler, tester, déployer — deviennent chronophages et sources d'erreurs humaines. Le DevOps répond à ce problème en automatisant l'intégralité de la chaîne entre le commit du développeur et la mise en production.

Note technique Parle lentement dans les 30 premières secondes. Le public — et le prof — jugent ton calme au démarrage. Respire entre les phrases.
T+00:45 — Définitions clés
Poser le vocabulaire CI/CD
À dire

Deux concepts fondamentaux structurent notre projet. Premièrement, l'Intégration Continue, ou CI : à chaque modification du code, on lance automatiquement une série de vérifications — compilation, tests, analyse qualité. Deuxièmement, le Déploiement Continu, ou CD : on étend cette automatisation jusqu'à la livraison de l'artefact prêt à déployer. Notre projet illustre concrètement ces deux principes.

Démonstration GitHub Actions — les 7 jobs

Le pipeline prend environ 4 minutes. Tu as donc 5 minutes pour commenter les jobs un par un, au fur et à mesure qu'ils passent au vert. Ne te précipite pas : commente chaque job en détail, c'est ce que le prof attend.

T+07:30 — Job 1 : Lint
Checkstyle + SpotBugs
Action Cliquer sur le job Lint (Checkstyle + SpotBugs) dans la colonne de gauche dès qu'il passe au vert. Déplier la step "Checkstyle" pour montrer les logs.
À dire

Premier job, premier vert : le lint. C'est notre première barrière de qualité. Checkstyle vérifie le style du code — conventions de nommage, longueur des lignes, imports inutilisés. SpotBugs fait une analyse sémantique plus poussée : il détecte les NullPointerExceptions potentielles, les ressources non fermées, les bugs de sérialisation. Nous avons configuré ces outils en mode informationnel : ils rapportent les violations sans bloquer le pipeline, car le code applicatif existait avant l'introduction du lint et contient 177 violations Checkstyle. Les rapports XML sont disponibles en téléchargement comme artefacts GitHub Actions.

Pourquoi insister sur le mode informationnel C'est un choix pragmatique qui montre une réflexion d'ingénieur, pas un compromis paresseux. Si le prof challenge : "Sur un projet greenfield, on aurait Checkstyle bloquant dès le premier commit. Sur du legacy, on accepte la dette technique et on la résorbe progressivement."
T+08:00 — Job 2 : Tests
JUnit 5 + Mockito + JaCoCo
Action Cliquer sur Tests dans la colonne gauche. Déplier la step "Tests unitaires (Surefire)" pour montrer la ligne Tests run: 15, Failures: 0.
À dire

Deuxième job : les tests. Maven Surefire exécute en premier les 15 tests unitaires sur les classes utilitaires PasswordUtil et BiblioUtils — la logique métier pure, sans dépendance à la base de données. Puis Maven Failsafe exécute 6 tests d'intégration sur la couche REST. Pour ces tests, le DAO est remplacé par un mock Mockito, ce qui nous permet de tester sans démarrer Oracle. C'est une décision architecturale clé : Oracle XE met deux à trois minutes à démarrer, ce qui serait inacceptable à chaque commit. Notre stratégie de mocking nous permet de tester en moins de 10 secondes. JaCoCo génère un rapport de couverture XML qui sera consommé par SonarCloud à l'étape suivante.

Points-clés à souligner
  • 21 tests, 0 failure, 0 error
  • 10 secondes d'exécution vs 3 minutes avec Oracle
  • Architecture hexagonale : la logique métier est isolée de la couche persistance
T+09:00 — Job 3 : Quality / SonarCloud
Analyse qualité 600+ règles
Action Cliquer sur SonarCloud dans la colonne gauche. Montrer la commande Maven qui s'exécute.
À dire

Troisième job, en parallèle du suivant : l'analyse qualité avec SonarCloud. Le code source et le rapport JaCoCo sont envoyés à SonarCloud, qui applique plus de 600 règles classifiées en trois familles : Reliability — la fiabilité ; Maintainability — la maintenabilité ; et Security — la sécurité, avec les classifications OWASP et CWE. SonarCloud calcule également une Quality Gate, qui est un ensemble de seuils définissant l'acceptabilité du code — par exemple, plus de 80% de couverture sur le nouveau code, zéro bug critique. En CI/CD strict, une Quality Gate FAILED peut bloquer le merge d'une Pull Request.

T+09:30 — Job 4 : Package
Construction du WAR Maven
Action Cliquer sur Package WAR. Montrer la step "Build du WAR" et la step "Publication du WAR" qui upload l'artifact.
À dire

Quatrième job : le packaging. Maven compile le code et assemble toutes les classes, ressources et dépendances dans un fichier WAR — c'est l'artefact applicatif livrable. Ce WAR est ensuite uploadé comme artefact GitHub, conservé sept jours, téléchargeable depuis l'interface. Cela permet à un opérateur, en cas d'incident, de redéployer manuellement une version précise sans avoir à reconstruire. C'est ce qu'on appelle un artifact registry, et c'est un élément critique de la traçabilité en production.

T+10:30 — Job 5 : Docker
Build multi-stage + Push multi-registry
Action Cliquer sur Docker Build & Push. Déplier "Build et Push" pour montrer le build des layers.
À dire

Cinquième job, et le plus impressionnant : la construction de l'image Docker et sa publication. Notre Dockerfile est en multi-stage : un premier stage avec Maven et le JDK pour compiler le WAR, puis un deuxième stage avec uniquement Tomcat, qui copie le WAR depuis le premier stage. Le builder est ensuite jeté. Résultat : une image runtime de 450 mégaoctets au lieu d'1,2 gigaoctets, et surtout une surface d'attaque réduite — pas de Maven, pas de code source dans l'image livrée. Une fois construite, l'image est publiée simultanément sur deux registres : Docker Hub, qui est le registre public historique, et GitHub Container Registry, qui s'intègre nativement au dépôt. Chaque image est taguée avec "latest" et avec le SHA du commit, ce qui permet un rollback précis vers n'importe quelle version antérieure.

Mots techniques à placer Layer, multi-stage, surface d'attaque, registre, tag, immutable, rollback.
T+11:30 — Job 6 : Security / Trivy
Scan de vulnérabilités CVE
Action Cliquer sur Scan sécurité Trivy. Si possible, montrer le tableau des CVE détectées dans les logs.
À dire

Sixième job : le scan de sécurité avec Trivy. Là où SonarCloud regardait le code source, Trivy regarde l'image livrée — c'est complémentaire. Trivy compare chaque paquet installé dans l'image — paquets OS comme openssl, dépendances Java, fichiers de configuration — avec une base de données de vulnérabilités connues, les CVE. Chaque CVE a un identifiant standardisé, format CVE-année-numéro, et un score CVSS de 0 à 10. Le résultat est uploadé au format SARIF, qui est le standard de l'industrie pour les rapports d'analyse statique, et apparaît dans l'onglet Security de GitHub.

Si le prof demande la différence Sonar vs Trivy "Sonar = code source, Trivy = image construite. Sonar voit ce que vous écrivez, Trivy voit ce que vous livrez réellement à vos clients. Les deux sont nécessaires pour une politique de sécurité shift-left complète."
T+11:45 — Job 7 : Notify / Slack
Notification d'équipe
Action Cliquer sur Notification Slack. Si Slack est configuré, basculer vers Slack pour montrer le message reçu.
À dire

Septième et dernier job : la notification d'équipe via Slack. Personne en équipe ne va manuellement vérifier l'onglet Actions à chaque commit. La notification automatique est le seul moyen d'avoir une boucle de feedback courte entre push et statut. Notre job inclut une condition particulière : if always(), qui signifie qu'il s'exécute même si un job précédent a échoué. C'est crucial — on veut être notifié surtout en cas d'échec. C'est ce qu'on appelle le principe fail fast : détecter et signaler les problèmes le plus tôt possible.

T+12:15 — Détailler chaque métrique
À dire en pointant chaque chiffre

Les Bugs sont des erreurs avérées de logique — null pointer, divisions par zéro. Les Vulnerabilities sont des failles de sécurité confirmées, classifiées selon les standards OWASP et CWE. Les Security Hotspots sont du code à risque qui mérite une revue humaine — différent d'une vulnérabilité confirmée, c'est un "à vérifier". Les Code Smells sont des symptômes de mauvaise conception qui suggèrent du refactoring : méthodes trop longues, complexité élevée, code dupliqué. La Coverage est calculée à partir du rapport JaCoCo que notre pipeline a uploadé.

T+12:35 — Anticiper la couverture faible
À dire — important d'anticiper

Vous remarquerez que notre couverture est volontairement faible, autour de 8%. C'est un choix : nous testons uniquement la logique métier pure et la couche REST. C'est une évolution future identifiée dans notre rapport. Le principe de la pyramide des tests est respecté : beaucoup d'unitaires rapides à la base, peu d'intégration au milieu.

Si le prof challenge sur la couverture "La couverture absolue n'est pas un objectif en soi — c'est la couverture de la logique métier critique qui compte. Tester un getter à 100% n'apporte rien. Une couverture de 80% sur le code business vaut mieux qu'une couverture de 95% diluée sur tout."

Questions probables du professeur

Voici les 20 questions les plus probables sur ta pipeline spécifique. Chaque réponse est calibrée pour 30-60 secondes, avec une structure : réponse directe → justification technique → ouverture.

🎯 Sur les choix d'architecture

Pourquoi 7 jobs et pas 1 seul gros job avec toutes les commandes ?

Trois raisons : parallélisme — quality et package tournent en même temps, ce qui réduit la durée totale ; fail fast — si lint échoue, on n'exécute pas les 6 jobs suivants et on économise des ressources ; observabilité — chaque job a son propre log et son propre statut dans l'UI, ce qui facilite considérablement le debugging.

Pourquoi avoir choisi GitHub Actions plutôt que Jenkins ?

GitHub Actions est intégré nativement à notre dépôt, sans configuration de webhook. Sa marketplace de 21 000+ actions évite de réécrire des scripts d'infrastructure. Et c'est gratuit illimité pour les repos publics. Jenkins aurait été pertinent dans un contexte d'entreprise avec contraintes on-premise — pour un projet pédagogique, GitHub Actions était le choix le plus rationnel. Nous avons quand même implémenté Jenkins dans le Jenkinsfile pour démontrer la portabilité.

Pourquoi pousser sur Docker Hub et GHCR ?

Trois raisons : redondance — si Docker Hub a un incident, GHCR reste accessible ; simplicité d'auth — sur GHCR, l'authentification utilise le GITHUB_TOKEN auto-généré, donc zéro setup ; contournement des rate limits — Docker Hub limite à 100 pulls anonymes par 6 heures sur le plan gratuit, ce qui peut casser un CI/CD à fort trafic. GHCR n'a pas ce problème.

🧪 Sur les tests

Pourquoi ne pas tester avec une vraie base Oracle ?

Oracle XE met 90 secondes à 3 minutes pour démarrer. Multiplié par chaque commit, c'est inacceptable — un développeur ferait 20 pushs par jour, soit 1h+ de temps mort. Nous utilisons donc Mockito pour remplacer les DAOs par des mocks. Cela isole la logique métier, conformément au principe d'architecture hexagonale. Pour des tests d'intégration réels, on utiliserait Testcontainers, qui démarre Oracle dans un conteneur juste pour les tests — c'est une évolution future identifiée.

8% de couverture, c'est très peu, non ?

C'est volontaire et défendable. Nous testons uniquement la logique métier pure et la couche REST avec mocks. Les Servlets sont des intégrateurs HTTP — peu de logique métier, beaucoup de plomberie, peu de valeur à tester unitairement. Les DAOs nécessiteraient une vraie base. La règle d'or : la couverture absolue n'est pas un objectif en soi — c'est la couverture du code business critique qui compte. Tester un getter à 100% n'apporte rien.

Quelle est la différence entre Mockito et un stub manuel ?

Un stub manuel est une classe que vous écrivez à la main qui implémente l'interface du DAO — verbeux, fragile, doit être maintenu à chaque changement de l'interface. Mockito génère ces stubs à la volée par bytecode, et permet une syntaxe expressive avec when/thenReturn pour configurer les retours, et verify pour vérifier les appels. C'est devenu le standard de facto en Java.

🔐 Sur la sécurité

Comment GitHub stocke-t-il les secrets ?

Chiffrement asymétrique : le navigateur chiffre la valeur avec la clé publique du dépôt avant l'envoi. GitHub ne stocke que la version chiffrée — personne, même pas Microsoft, ne peut la lire sans la clé privée. Au runtime, le runner déchiffre juste-à-temps. Et GitHub masque automatiquement toute valeur secrète qui apparaîtrait dans les logs avec des astérisques. C'est conforme au principe Zero Trust.

Que faire si un secret fuite par accident ?

Rotation immédiate, sans débat : révoquer le token compromis, en générer un nouveau, mettre à jour le secret dans GitHub. D'abord rotation, ensuite enquête. Ne jamais penser "ce n'était que dans tel canal privé" — un secret exposé doit être considéré comme cassé. C'est ce qu'on appelle le principe "assume breach" en cybersécurité.

À quoi sert Trivy par rapport à Sonar ?

Sonar regarde le code source que vous écrivez. Trivy regarde l'image que vous livrez. Les deux sont complémentaires et nécessaires. Une image peut être propre côté code source mais contenir un paquet OS avec une CVE critique — par exemple openssl avec une faille récente. Seul Trivy détectera ce cas. C'est la philosophie shift-left : intégrer les contrôles sécurité dans la CI/CD plutôt qu'en audit annuel.

🐳 Sur Docker

Pourquoi multi-stage et pas single-stage ?

Pour séparer build et runtime. Le stage builder contient Maven, le JDK complet, le cache des dépendances, et le code source — il fait environ 1,2 gigaoctets. Le stage runtime ne contient que Tomcat et le WAR final — environ 450 mégaoctets. On jette le builder à la fin. Résultat : image deux fois plus petite, pull plus rapide en production, et surtout surface d'attaque considérablement réduite — un attaquant ne peut pas exploiter un Maven qui n'existe pas dans l'image.

Qu'est-ce qu'une layer Docker ?

C'est l'unité de stockage immutable d'une image. Chaque instruction du Dockerfile — RUN, COPY, ADD — crée une nouvelle layer. Les layers sont stockées en UnionFS, ce qui permet la déduplication entre images. Quand vous faites docker pull, Docker ne télécharge que les layers que vous n'avez pas déjà localement. Le tag final est en fait un manifest qui pointe vers une liste de layers ordonnées.

Pourquoi exécuter le conteneur sous un utilisateur non-root ?

Par défaut, Docker exécute le processus principal en root à l'intérieur du conteneur. Si un attaquant compromet l'application — par injection ou autre vulnérabilité — il dispose alors de root dans le conteneur. Avec certaines mauvaises configurations, comme le montage du Docker socket ou des capabilities Linux non isolées, il peut s'échapper et compromettre l'hôte. En passant en USER tomcat, on limite cet impact même en cas de compromission applicative.

🚀 Sur le DevOps

Continuous Delivery vs Continuous Deployment, quelle différence ?

CD Delivery : l'artefact est prêt à déployer après chaque pipeline, mais le déploiement reste manuel — c'est notre cas. CD Deployment : le déploiement en production est lui aussi automatique. Notre pipeline s'arrête à la publication de l'image. Le passage en Deployment nécessiterait un cluster Kubernetes et un GitOps comme ArgoCD pour observer le registre et synchroniser le cluster — c'est notre évolution future.

Quelles métriques utiliseriez-vous pour mesurer votre CI/CD ?

Les 4 métriques DORA, qui sont devenues le standard de l'industrie : Deployment Frequency — combien de fois on déploie ; Lead Time for Changes — temps entre commit et production ; Change Failure Rate — pourcentage de déploiements qui causent une régression ; Mean Time to Restore — temps de récupération après incident. Les équipes haute performance déploient plusieurs fois par jour avec moins de 15% d'échecs.

Quelles sont les évolutions futures de votre projet ?

À court terme : intégrer Testcontainers pour tester contre une vraie Oracle dans la CI ; ajouter Renovate pour la mise à jour automatique des dépendances ; durcir le Quality Gate Sonar. À moyen terme : passer en Continuous Deployment vers un cluster Kubernetes via Helm et ArgoCD ; ajouter l'observabilité avec Prometheus et Grafana. À long terme : feature flags via LaunchDarkly, tests de charge automatisés avec k6, signatures d'artefacts avec Cosign pour la supply chain security.

🛠️ Sur des points spécifiques de notre code

À quoi sert le if: always() sur le job notify ?

Par défaut, GitHub Actions stoppe les jobs qui dépendent d'un job raté. Or, on veut être notifié surtout en cas d'échec — ce serait absurde de ne recevoir des notifications que pour les succès. Le if: always() garantit l'exécution du job quel que soit le résultat des dépendances. C'est un pattern standard pour les notifications, le nettoyage de ressources, ou les rapports finaux.

Pourquoi continue-on-error: true sur SpotBugs ?

Choix pragmatique : notre code applicatif contient des warnings SpotBugs liés à la nature même de JPA — par exemple EI_EXPOSE_REP sur les collections d'entités, qui est structurellement nécessaire pour qu'Hibernate puisse gérer les relations. Bloquer la pipeline sur ces warnings n'aurait pas de sens. Avec continue-on-error, le job reste vert mais le rapport est uploadé en artifact pour consultation. C'est un compromis assumé documenté dans le rapport.

Pourquoi les jobs quality, docker, security ne tournent que sur main ?

Trois raisons : quotas — SonarCloud a des limites sur le plan gratuit ; pollution — pousser une image à chaque PR encombrerait le registre Docker Hub avec des versions intermédiaires inutilisables ; vitesse — on veut un feedback rapide sur les PR, donc seulement lint + test + package, qui prennent moins de 2 minutes. Le pipeline complet ne s'exécute qu'au moment de la fusion sur main.

Si la pipeline rate, comment vous reprenez ?

Diagnostic en 5 étapes : (1) lire le message d'erreur exact dans l'UI Actions ; (2) identifier le step précis qui rate ; (3) reproduire localement avec la même commande Maven ou Docker ; (4) si reproductible, fix local puis push ; si non, c'est une différence d'environnement à investiguer. Sur ce projet, nous avons rencontré et résolu six problèmes concrets — bloc env dupliqué, version Trivy retirée, secrets vides, etc. — tous documentés dans le rapport.

Qu'est-ce que actions/checkout@v4 exactement ?

C'est une action GitHub officielle, version 4, qui clone le code source du dépôt dans le runner. Sans elle, le runner n'aurait pas accès au code à compiler. La notation @v4 est un pinning de version : on s'assure de la reproductibilité du build en figeant la version. Les meilleures pratiques de sécurité supply chain recommandent même de pinner le SHA exact plutôt que la tag majeure, mais c'est un compromis avec la maintenance.
