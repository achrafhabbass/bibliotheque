Chapitre 01

Présentation générale du projet

1.1 Objectif du projet

Ce projet s'inscrit dans le module Gestion des Projets IT et traite le Sujet 1 : CI/CD moderne multi-outils. L'objectif est de démontrer la maîtrise des concepts modernes d'intégration et de déploiement continus en appliquant une pipeline CI/CD complète à une application web réelle.

L'application support, BiblioGest, est un système de gestion de bibliothèque développé en Jakarta EE 10. Mais l'application n'est pas le cœur du projet : ce qui compte, c'est la chaîne d'automatisation qui l'entoure.

💡 En une phrase
À partir d'un simple git push, toute la chaîne d'intégration s'exécute automatiquement : analyse de code → tests → qualité → packaging → containerisation → scan de vulnérabilités → notification d'équipe. Sans aucune intervention humaine.

1.2 Problématique

Le développement logiciel moderne fait face à une contradiction : plus un projet grandit, plus les tâches répétitives (compiler, tester, déployer) deviennent chronophages et sources d'erreurs humaines.

La CI/CD répond à cinq questions concrètes :

  1. Comment garantir que le code compile sur la machine de chacun ? → en l'exécutant sur un environnement standardisé à chaque push.
  2. Comment éviter les régressions ? → en relançant tous les tests automatiquement à chaque modification.
  3. Comment livrer une version reproductible ? → en générant un artifact (WAR + image Docker) versionné par commit.
  4. Comment garantir un niveau de qualité minimal ? → en mesurant lint, couverture, complexité via Sonar et en bloquant le merge si seuil non atteint.
  5. Comment réduire la surface d'attaque sécurité ? → en scannant les CVE de l'image avec Trivy à chaque build.

Chapitre 02

L'application BiblioGest

2.1 Description fonctionnelle

BiblioGest est une application web de gestion de bibliothèque. Les utilisateurs authentifiés (managers ou administrateurs) gèrent :

  • Le catalogue : livres, auteurs, catégories
  • Les clients : inscriptions, contacts
  • Les emprunts : prêts, retours, calcul automatique des frais et pénalités
  • Les utilisateurs : gestion des comptes (admin uniquement)

Règles métier

  • Un livre marqué non disponible ne peut pas être emprunté.
  • Un client ne peut avoir qu'un emprunt EN_COURS par livre.
  • À la création d'un emprunt : frais = dureeJours × tarifJournalier.
  • Au retour avec retard : pénalité = joursExcès × tarifJournalier × 1.5.
  • La suppression du dernier administrateur est bloquée.

Chapitre 03

La pipeline CI/CD en détail

La pipeline est composée de 7 jobs qui s'enchaînent dans un graphe de dépendances (DAG). Ce chapitre décrypte chaque job : son rôle, ce qu'il fait techniquement, les commandes qu'il exécute, ses outputs, ses risques et les erreurs fréquemment rencontrées.

[1.Lint] → [2.Tests] → [3.Quality] │ └─► [4.Package] → [5.Docker] → [6.Security] → [7.Notify]

3.1 Job 1 — Lint (Checkstyle + SpotBugs)

Rôle

Effectuer l'analyse statique du code source avant même de tenter une compilation complète ou des tests. C'est la première barrière de qualité : elle attrape les défauts visibles à l'œil (style, conventions) et certains bugs sémantiques (NPE potentielles, ressources non fermées).

Pourquoi il existe ?

Coût d'un bug détecté à différents stades (étude IBM, ordre de grandeur) :

  • Lint local : ×1
  • Test unitaire : ×5
  • Test d'intégration : ×15
  • Production : ×100

Plus le bug est attrapé tôt, moins il coûte. Le lint est l'étape la plus précoce.

Ce qu'il fait techniquement

  1. Checkout du code source
  2. Installation de Java 17 Temurin + activation du cache Maven
  3. Exécution de mvn -B checkstyle:check
  4. Compilation préalable (mvn -B compile -DskipTests)
  5. Exécution de mvn -B spotbugs:check
  6. Upload des rapports XML comme artefacts GitHub

Outputs générés

  • target/checkstyle-result.xml — 177 violations dans notre cas
  • target/spotbugsXml.xml — 32 bugs détectés
  • Artifact lint-reports téléchargeable depuis l'UI GitHub

Risques & erreurs fréquentes

3.2 Job 2 — Tests (JUnit + JaCoCo)

Rôle

Exécuter les tests unitaires (logique pure) puis les tests d'intégration (couche REST avec mocks), et générer un rapport de couverture JaCoCo qui alimentera SonarCloud.

Pourquoi il existe ?

Les tests sont le filet de sécurité qui empêche les régressions. Sans tests automatiques, chaque modification doit être validée manuellement — irréaliste à l'échelle d'une équipe. La pipeline garantit que tous les tests passent sur tous les commits avant qu'on puisse merger.

Ce qu'il fait techniquement

mvn test    - exécute *Test.java (Surefire)
mvn verify  - exécute *IT.java (Failsafe) + agrégation JaCoCo

Outputs

  • target/surefire-reports/TEST-*.xml — résultats unitaires
  • target/failsafe-reports/TEST-*.xml — résultats d'intégration
  • target/site/jacoco/jacoco.xml — rapport de couverture (consommé par Sonar)
  • target/site/jacoco/index.html — rapport HTML cliquable

Statistiques du projet

  • Tests unitaires : 15 (BiblioUtilsTest + PasswordUtilTest)
  • Tests d'intégration : 6 (LivreResourceIT)
  • Total : 21 tests, durée moyenne ~10 s
  • Couverture : ~8 % (volontairement faible, focus sur la logique métier)

Risques & erreurs fréquentes

3.3 Job 3 — Quality (SonarCloud)

Rôle

Envoyer le code source et le rapport JaCoCo à SonarCloud pour une analyse qualité approfondie : bugs, vulnérabilités, code smells, hotspots de sécurité, duplication, couverture, dette technique. SonarCloud calcule ensuite une Quality Gate (note A à E) qui peut bloquer le merge.

Pourquoi il existe ?

Le lint local détecte les défauts évidents. Sonar va beaucoup plus loin : il croise une base de plus de 600 règles, applique des heuristiques de sécurité (OWASP, CWE), mesure la complexité cyclomatique, et compare avec le code de référence. C'est l'outil de qualité standard de l'industrie.

Ce qu'il fait techniquement

mvn -B verify sonar:sonar \
  -Dsonar.projectKey=$SONAR_PROJECT_KEY \
  -Dsonar.organization=$SONAR_ORGANIZATION \
  -Dsonar.host.url=https://sonarcloud.io

Outputs

Aucun fichier local. Les résultats sont visibles sur le dashboard SonarCloud : sonarcloud.io/dashboard?id=achrafhabbass_bibliotheque.

3.4 Job 4 — Package (Build WAR)

Rôle

Produire l'artefact applicatif livrable : le fichier WAR. C'est ce qui sera ensuite copié dans l'image Docker au job suivant.

Pourquoi il existe ?

Le packaging est l'étape de matérialisation : tant qu'on n'a qu'un arbre de fichiers target/classes/, on n'a rien de déployable. Le WAR compresse tout en un binaire unique, versionné, archivable, déployable.

Ce qu'il fait techniquement

mvn package -DskipTests -B --no-transfer-progress

On utilise -DskipTests ici parce que les tests ont déjà été exécutés au job précédent — pas besoin de les relancer.

Outputs

  • target/bibliotheque.war — ~33 Mo
  • Artifact GitHub nommé bibliotheque-war téléchargeable 7 jours

3.5 Job 5 — Docker (Build + Push)

Rôle

Construire l'image Docker qui contient le WAR + Tomcat configuré, puis la publier sur deux registres : Docker Hub (public) et GitHub Container Registry (intégré au repo).

Pourquoi il existe ?

Un WAR seul ne suffit pas : il faut un serveur d'application configuré autour. L'image Docker capture toute l'infrastructure runtime — JVM, Tomcat, dépendances système, variables d'environnement. C'est ce qu'on appelle le principe "build once, run anywhere".

Ce qu'il fait techniquement

  1. Configuration Docker Buildx (build multi-plateforme)
  2. Authentification Docker Hub via docker/login-action
  3. Authentification GHCR via GITHUB_TOKEN (automatique)
  4. Génération de tags via docker/metadata-action :
    • latest (toujours la dernière version)
    • <sha-du-commit> (immutable, traçable)
  5. Build + push simultané vers les deux registres

Outputs

  • achrafhb/bibliotheque:latest sur Docker Hub
  • ghcr.io/achrafhabbass/bibliotheque:latest sur GHCR
  • Mêmes images également taggées avec le SHA du commit

3.6 Job 6 — Security Scan (Trivy)

Rôle

Scanner l'image Docker fraîchement publiée à la recherche de CVE (Common Vulnerabilities and Exposures) connues : paquets OS, dépendances Java, mauvaises configurations, secrets exposés.

Pourquoi il existe ?

Sonar regarde le code source. Trivy regarde l'image livrée. C'est la dernière barrière avant que l'image ne parte en production. Un seul paquet vulnérable (ex: openssl avec CVE-2024-XYZ critique) peut suffire à compromettre tout le serveur — d'où l'intérêt du scan systématique.

Ce qu'il fait techniquement

  1. Scan en mode table pour l'affichage humain dans les logs
  2. Scan en mode sarif pour upload vers GitHub Security
  3. Upload du SARIF via github/codeql-action/upload-sarif

Outputs

  • Logs CLI avec tableau des CVE par sévérité
  • Onglet Security du repo GitHub peuplé avec les vulnérabilités

3.7 Job 7 — Notify (Slack)

Rôle

Notifier l'équipe via Slack à la fin de chaque pipeline, avec un statut coloré (vert = succès, rouge = échec) et des liens directs vers le run.

Pourquoi il existe ?

Personne ne va manuellement vérifier l'onglet Actions à chaque commit. La notification automatique est le seul moyen d'avoir une boucle de feedback courte entre push et statut. C'est la pierre angulaire du "fail fast" en CI/CD.

Ce qu'il fait techniquement

  1. Step status : calcule succès / échec via contains(needs.*.result, 'failure')
  2. Step slack : POST JSON formaté vers le webhook Slack

Particularité

Le job a if: always() — il s'exécute même si un job précédent a échoué. C'est volontaire : on veut être notifié surtout en cas d'échec.

Chapitre 04

Les 16 outils utilisés

4.1 GitHub Actions ⭐ (outil principal)

Définition simple : service d'automatisation intégré à GitHub qui exécute des workflows à chaque événement Git.

Rôle dans le projet : moteur principal de la pipeline. Le fichier .github/workflows/ci-cd.yml définit les 7 jobs.

Fonctionnement interne : à chaque push, GitHub déclenche un runner (VM Ubuntu) qui clone le repo et exécute les steps. Les jobs peuvent dépendre les uns des autres via needs:. Les actions de la marketplace sont des modules réutilisables (ex: actions/checkout@v4).

Vocabulaire technique : workflow, job, step, runner, marketplace, action, artifact, secret, variable, environment, matrix build, reusable workflow.

Avantages : marketplace de 21 000+ actions, gratuit illimité pour OSS, intégration native GitHub, syntaxe YAML lisible, support multi-OS (Ubuntu, Windows, macOS).

Inconvénients : verrouillage à GitHub, quota plus limité pour repos privés, debugging en SSH non disponible nativement.

Cas d'usage en entreprise : startups et équipes hébergées sur GitHub. Microsoft, GitHub eux-mêmes, Vercel, Stripe l'utilisent en interne.

4.2 GitLab CI/CD

Définition simple : système CI/CD natif de la plateforme GitLab.

Rôle dans le projet : pipeline alternative démontrée dans .gitlab-ci.yml.

Fonctionnement : pipeline organisée en stages séquentiels. Tous les jobs d'un même stage tournent en parallèle. Runners auto-hébergeables ou shared.

Vocabulaire : stage, job, runner, pipeline, artifact, cache, rules, needs, environment, deploy, manual job.

Avantages : DevOps tout-en-un (SCM + CI + registry + monitoring), interface visualisation excellente, self-hosted très mature.

Inconvénients : marketplace plus restreint qu'Actions, syntaxe rules: complexe.

4.3 Jenkins

Définition simple : serveur d'automatisation open-source historique (depuis 2011), 100% self-hosted.

Rôle dans le projet : pipeline alternative démontrée dans Jenkinsfile.

Fonctionnement : un serveur Jenkins lance des "agents" (workers). Chaque pipeline est définie en Groovy DSL dans un Jenkinsfile versionné avec le code.

Vocabulaire : pipeline (declarative vs scripted), stage, step, agent, node, plugin, credentials, build, parameter, trigger.

Avantages : 100% open source, 1 900+ plugins, flexibilité maximale, intégration aux outils legacy d'entreprise (LDAP, AD, JIRA).

Inconvénients : courbe d'apprentissage élevée, maintenance plugins, UI vieillissante, pas de mode SaaS officiel.

4.4 CircleCI

Définition simple : plateforme CI/CD SaaS axée performance et réutilisabilité.

Rôle dans le projet : pipeline alternative démontrée dans .circleci/config.yml.

Fonctionnement : workflows composés de jobs, chaque job tourne dans un executor (Docker, machine VM, macOS). Les orbs sont des modules YAML réutilisables.

Vocabulaire : workflow, job, executor, orb, resource class, workspace, parallelism, approval job.

Avantages : performances élevées, debugging SSH dans le runner, multi-VCS (GitHub, GitLab, Bitbucket).

Inconvénients : plan gratuit limité (6 000 min/mois), moins d'intégrations natives qu'Actions.

4.5 Travis CI

Définition simple : pionnier des CI/CD SaaS pour OSS, en déclin depuis 2021.

Rôle dans le projet : pipeline alternative démontrée dans .travis.yml.

Fonctionnement : syntaxe minimaliste, configure le langage et exécute des scripts.

Avantages : la syntaxe la plus concise des cinq moteurs, idéal pour démarrer.

Inconvénients : plan gratuit OSS supprimé en 2021, communauté en fuite vers GitHub Actions.

4.6 Docker

Définition simple : technologie de conteneurisation qui empaquette une application avec toutes ses dépendances dans un environnement isolé et portable.

Rôle dans le projet : utilisé pour le packaging final (image runtime) et pour le développement local (Oracle XE + app dans docker-compose.yml).

Fonctionnement interne : Docker utilise les namespaces et cgroups du noyau Linux pour isoler processus, réseau, filesystem. Une image est constituée de couches en lecture seule (un layer par instruction du Dockerfile) ; le conteneur ajoute une couche en lecture/écriture.

Vocabulaire : image, container, layer, Dockerfile, registry, tag, volume, network, healthcheck, ENTRYPOINT, CMD, multi-stage build.

Avantages : reproductibilité, isolation, légèreté (vs VM), écosystème massif.

Inconvénients : courbe d'apprentissage initiale, sécurité demande de la rigueur (user non-root, scan CVE).

4.7 SonarCloud / SonarQube

Définition simple : plateforme d'analyse continue de la qualité du code.

Différence : SonarQube = on-premise (à installer). SonarCloud = SaaS (cloud Sonar). Même moteur d'analyse, deux modes de déploiement.

Rôle dans le projet : analyse de qualité après chaque push sur main.

Fonctionnement : 600+ règles couvrant bugs, vulnérabilités (OWASP, CWE), code smells, hotspots de sécurité, duplication. Note Quality Gate (A à E) basée sur des seuils configurables.

Vocabulaire : Quality Gate, code smell, technical debt, hotspot, coverage, duplication, reliability, maintainability, security rating.

4.8 Maven

Définition simple : outil de build et de gestion de dépendances pour Java.

Rôle dans le projet : compile, teste, package, lance Sonar, lance Checkstyle, lance SpotBugs.

Fonctionnement : suit le cycle de vie standard (validate → compile → test → package → verify → install → deploy). Le pom.xml déclare dépendances et plugins.

Vocabulaire : POM, dependency, scope (compile, provided, test, runtime), plugin, goal, phase, lifecycle, profile, repository.

4.9 JUnit 5

Définition simple : framework de tests automatisés pour Java.

Rôle : écrire et exécuter les tests unitaires et d'intégration.

Vocabulaire : @Test, @BeforeEach, @AfterEach, assertion, fixture, parameterized test, dynamic test, extension.

4.10 Mockito

Définition simple : librairie de mocking pour Java.

      run: mvn -B compile -DskipTests --no-transfer-progress

  • Deux docker/login-action consécutifs : Docker Hub + GHCR.

notify:

  if: always() && github.ref == 'refs/heads/main'

      run: |
        if [ "${{ contains(needs.*.result, 'failure') }}" = "true" ]; then

Chapitre 07

Analyse du Dockerfile multi-stage

7.1 Le concept multi-stage

Un Dockerfile simple (single-stage) ressemble à :

FROM maven:3.9-temurin-17
COPY . /app
RUN mvn package
CMD ["java", "-jar", "/app/target/app.war"]

Problème : l'image finale contient Maven (~200 Mo), le JDK complet, le code source, le cache des dépendances. Au total ~1 Go. C'est gros, lent à puller, et présente une surface d'attaque inutile en production.

Le multi-stage résout ce problème en séparant build et runtime :

7.2 Notre Dockerfile

# ===== Stage 1 : Build Maven =====
FROM maven:3.9-eclipse-temurin-17 AS builder
WORKDIR /build

# Cache des dépendances : copier d'abord pom.xml seul
COPY pom.xml ./
RUN mvn -B dependency:go-offline --no-transfer-progress || true

# Puis copier le code source et compiler
COPY src ./src
COPY checkstyle.xml ./
RUN mvn -B package -DskipTests --no-transfer-progress

# ===== Stage 2 : Runtime Tomcat =====
FROM tomcat:10.1-jdk17-temurin AS runtime

LABEL org.opencontainers.image.title="BiblioGest"

# Nettoyage des webapps par défaut
RUN rm -rf /usr/local/tomcat/webapps/*

# Récupération du WAR depuis le stage builder
COPY --from=builder /build/target/bibliotheque.war \
                  /usr/local/tomcat/webapps/ROOT.war

ENV DB_URL=jdbc:oracle:thin:@oracle-xe:1521/XEPDB1 \
    DB_USER=biblio \
    JAVA_OPTS="-XX:+UseContainerSupport -XX:MaxRAMPercentage=75.0"

# Installation de wget pour le healthcheck
RUN apt-get update && apt-get install -y --no-install-recommends wget && \
    rm -rf /var/lib/apt/lists/*

# Utilisateur non-root pour la sécurité
RUN groupadd -r tomcat && useradd -r -g tomcat tomcat && \
    chown -R tomcat:tomcat /usr/local/tomcat
USER tomcat

EXPOSE 8080

HEALTHCHECK --interval=30s --timeout=10s --start-period=90s --retries=3 \
    CMD wget -qO- http://localhost:8080/api/livres >/dev/null 2>&1 || exit 1

CMD ["catalina.sh", "run"]

7.3 Décortiquage instruction par instruction

Stage 1 — Builder

  • FROM maven:3.9-eclipse-temurin-17 AS builder : image avec Maven + JDK17. AS builder nomme ce stage.
  • WORKDIR /build : crée et entre dans /build.
  • COPY pom.xml ./ : on copie d'abord le POM seul.
  • RUN mvn dependency:go-offline : télécharge toutes les dépendances. Cette couche est mise en cache si pom.xml ne change pas.
  • COPY src ./src : maintenant on copie le code source.
  • RUN mvn package : compile et produit le WAR.
🎯 Astuce performance
L'ordre COPY pom.xml → RUN dependency → COPY src permet à Docker de réutiliser la couche des dépendances même si le code change. Sans cette astuce, chaque modification du moindre fichier source re-téléchargerait toutes les dépendances Maven.

Stage 2 — Runtime

  • FROM tomcat:10.1-jdk17-temurin : base minimale (Tomcat + JDK, pas de Maven, pas de source).
  • RUN rm -rf /usr/local/tomcat/webapps/* : supprime les webapps Tomcat par défaut.
  • COPY --from=builder ... : copie uniquement le WAR depuis le stage 1. Le reste du stage 1 (Maven, source, .m2) est jeté.
  • USER tomcat : exécution non-root → bonne pratique sécurité.
  • HEALTHCHECK : vérifie l'app toutes les 30s. Docker reporte alors healthy ou unhealthy.

7.4 Sécurité — pourquoi USER non-root ?

Par défaut, un conteneur Docker tourne en root. Si un attaquant compromet l'application, il a root dans le conteneur. Avec les capacités Linux non isolées, certaines attaques permettent d'échapper au conteneur et de compromettre l'hôte.

En passant en USER tomcat, on limite considérablement l'impact : même une compromission applicative ne permet pas d'exécuter des opérations privilégiées dans le conteneur.

8.2 Pourquoi utiliser Mockito ?

Sans Mockito, on devrait soit :

  1. Démarrer Oracle dans la CI (lent et coûteux),
  2. Tester avec H2 en mémoire (compatibilité Oracle limitée),
  3. Écrire des stubs manuels (verbeux et fragile).

Mockito permet de remplacer une dépendance par un objet qui se comporte comme on veut :

@ExtendWith(MockitoExtension.class)
class LivreResourceIT {

    @Mock LivreDao dao;          // mock automatique
    LivreResource resource;

    @BeforeEach
    void setUp() {
        resource = new LivreResource(dao);   // injection via constructeur
    }

    @Test
    void getByIdInexistantRetourne404() {
        when(dao.findByIdWithRelations(99L)).thenReturn(null);  // scénario
        assertEquals(404, resource.getById(99L).getStatus());
    }
}

Le mock répond exactement ce qu'on lui demande. Le test isole la couche REST.

8.3 Pourquoi éviter Oracle dans la CI ?

  • Lenteur : démarrage de 90s à 3 min, multiplié par chaque commit = file d'attente.
  • Coût : Oracle est lourd en RAM (1-2 Go minimum).
  • Flakiness : healthchecks parfois imparfaits, tests intermittents.
  • Complexité : chargement schéma + données = code SQL fragile dans la pipeline.
💡 La règle
Pour les tests de composant ou de service, on mocke les dépendances externes. Pour les vrais tests bout-en-bout (end-to-end), on monte la stack complète — mais on les exécute moins souvent (nightly, pas à chaque commit).

8.4 JaCoCo — comment ça marche ?

JaCoCo est un agent Java. Il instrumente le bytecode au runtime : à chaque ligne, à chaque branche, à chaque méthode, il insère des compteurs. Quand les tests tournent, il enregistre quelles lignes ont été exécutées.

Configuration dans pom.xml :

<plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <executions>
        <execution>
            <goals><goal>prepare-agent</goal></goals>  <!-- attache l'agent au JVM des tests -->
        </execution>
        <execution>
            <id>report</id>
            <phase>verify</phase>
            <goals><goal>report</goal></goals>     <!-- génère target/site/jacoco -->
        </execution>
    </executions>
</plugin>

8.5 Pourquoi notre couverture est faible (~8%)

Volontairement, on ne teste que la logique métier pure (PasswordUtil, BiblioUtils) et l'API REST avec mocks.

On ne teste pas :

  • Les Servlets (couplage fort à HttpServletRequest/Response — difficile à mocker, faible valeur)
  • Les DAOs (nécessite Oracle, donc out-of-scope)
  • Les JSPs (frontend, hors champ unitaire)

Cette stratégie est cohérente avec le principe de la pyramide des tests : beaucoup d'unitaires (rapides), quelques tests d'intégration (moyens), très peu de tests end-to-end (lents).

▲ ╱ ╲ E2E ╱ ╲ (3-5 tests) ╱─────╲ ╱ ╲ INTEGRATION ╱ ╲ (10-30 tests) ╱───────────╲ ╱ ╲ UNITAIRES ╱ ╲ (centaines) ╱─────────────────╲

📚 Bloc 1 — Concepts généraux CI/CD

Quelle est la différence entre Continuous Integration, Continuous Delivery et Continuous Deployment ?
CI = automatiser build + tests à chaque push. CD (Delivery) = l'artefact est prêt à déployer après chaque pipeline réussie, mais le déploiement reste manuel. CD (Deployment) = le déploiement en production est lui aussi automatique. Notre projet est en mode Continuous Delivery : on publie l'image Docker, mais on n'a pas de cluster qui la consomme automatiquement.
Quels sont les bénéfices business du CI/CD ?
Time-to-market réduit (livraisons quotidiennes vs trimestrielles), feedback client plus rapide, qualité accrue par tests automatiques, réduction du coût de correction des bugs (×100 si détecté en prod vs CI), responsabilisation des équipes, audit trail complet via Git + pipeline.
Quels sont les piliers du DevOps ?
Le modèle CALMS : Culture (équipes Dev + Ops fusionnées), Automation (CI/CD, IaC), Lean (élimination du gaspillage), Measurement (métriques DORA), Sharing (transparence, partage de connaissances).
Quelles sont les métriques DORA et que mesurez-vous dans votre projet ?
Les 4 métriques DORA : Deployment Frequency, Lead Time for Changes, Change Failure Rate, Mean Time to Restore. Dans notre projet, on peut mesurer la fréquence de déploiement (un push = une image publiée) et le lead time (4-5 min entre push et notification Slack).

🛠️ Bloc 2 — Outils CI/CD

Pourquoi avoir choisi GitHub Actions comme outil principal ?
Quatre raisons : (1) intégration native avec notre dépôt GitHub, zéro configuration de webhook, (2) marketplace de 21 000+ actions évite de réécrire des scripts, (3) gratuit illimité pour les repos publics, (4) syntaxe YAML lisible. On a aussi implémenté GitLab CI, Jenkins, CircleCI et Travis CI pour démontrer la portabilité conceptuelle.
Quelle est la différence entre les stages de GitLab et les needs de GitHub Actions ?
GitLab utilise un modèle séquentiel : tous les jobs d'un stage tournent en parallèle, et le stage suivant attend la fin du précédent. GitHub Actions utilise un modèle DAG (Directed Acyclic Graph) plus flexible : chaque job déclare ses dépendances individuelles via needs:, ce qui permet des graphes arbitraires. Notre quality et package dépendent de test mais s'exécutent en parallèle.
Pourquoi Jenkins est-il considéré comme "l'ancêtre" mais toujours utilisé ?
Jenkins date de 2011, c'est le pionnier. Il est toujours utilisé en entreprise pour deux raisons : (1) self-hosted par nature, idéal quand les données ne peuvent pas quitter l'infra interne (banques, défense), (2) écosystème de 1 900+ plugins permet l'intégration avec n'importe quel outil legacy (LDAP, AD, JIRA). En contrepartie, courbe d'apprentissage élevée (Groovy DSL) et maintenance lourde.
Quelle est la différence entre SonarCloud et SonarQube ?
Même moteur d'analyse, deux modes de déploiement. SonarCloud est la version SaaS hébergée par SonarSource, gratuite pour les repos publics OSS, zéro maintenance. SonarQube Community est gratuit et auto-hébergé — pertinent quand le code est confidentiel. On a démontré les deux modes dans le projet via docker-compose.sonarqube.yml.

🐳 Bloc 3 — Docker

Pourquoi utiliser un Dockerfile multi-stage ?
Pour séparer build et runtime. Le stage builder contient Maven + JDK + source code (≈1 Go), nécessaire pour compiler. Le stage runtime ne contient que Tomcat + le WAR (≈450 Mo). On jette le builder à la fin. Résultat : image deux fois plus petite, surface d'attaque réduite, pull plus rapide.
Qu'est-ce qu'une couche (layer) Docker ?
Une couche est l'unité de stockage immutable d'une image Docker. Chaque instruction du Dockerfile (RUN, COPY, etc.) crée une nouvelle couche. Les couches sont stackées en UnionFS. Avantages : déduplication entre images, cache lors du rebuild, transfert partiel sur push/pull. Le tag final est en fait un manifest qui pointe vers une liste de couches.
Pourquoi exécuter le conteneur sous un utilisateur non-root ?
Par défaut, un conteneur tourne en root. En cas de compromission applicative, l'attaquant a root dans le conteneur. Avec certaines erreurs de configuration (capabilities Linux, montage Docker socket), il peut échapper au conteneur et compromettre l'hôte. En passant en USER tomcat, on limite l'impact même en cas de breach.
Pourquoi avoir 2 registres (Docker Hub + GHCR) ?
Trois raisons : (1) redondance — si Docker Hub a un incident, GHCR reste accessible, (2) simplicité d'auth sur GHCR via GITHUB_TOKEN auto-généré, (3) Docker Hub a des pull rate limits sur le plan gratuit (100 pulls/6h pour les anonymes). GHCR n'en a pas.
Comment fonctionne le cache Docker Buildx via GitHub Actions ?
cache-from: type=gha télécharge les layers du cache GitHub Actions, cache-to: type=gha,mode=max les ré-upload après le build. Cela réduit le build de ~2 min à ~30 s sur des changements mineurs. Le cache est invalidé si pom.xml change (nouvelle couche de dépendances).
Quel est le rôle de docker-compose dans votre projet ?
Docker Compose orchestre Oracle XE + l'app en local pour le développement et la démo. La directive depends_on.condition: service_healthy garantit que l'app attend que la PDB Oracle soit prête avant de démarrer. On a aussi un second fichier docker-compose.sonarqube.yml pour la démo SonarQube self-hosted.

🧪 Bloc 4 — Tests & Qualité

Quelle est la pyramide des tests ?
Modèle popularisé par Mike Cohn : beaucoup de tests unitaires (rapides, isolés) à la base, moins de tests d'intégration au milieu, très peu de tests end-to-end au sommet (lents, fragiles). Notre projet respecte ce principe : 15 tests unitaires, 6 tests d'intégration mockés, 0 test E2E (couvert par démo manuelle).
Pourquoi ne pas démarrer Oracle dans la CI ?
Oracle XE met 90 secondes à 3 minutes pour démarrer. Multiplié par chaque commit, c'est inacceptable. On utilise donc Mockito pour remplacer les DAOs par des mocks. La logique métier pure (BiblioUtils) ne dépend pas du tout de la DB. C'est une application directe du principe d'architecture hexagonale : isoler la logique métier des détails techniques.
Comment fonctionne Mockito techniquement ?
Mockito utilise la réflexion Java + la génération de bytecode (via ByteBuddy) pour créer une sous-classe dynamique de l'interface ou classe à mocker. Les méthodes du mock retournent des valeurs stubées via la syntaxe when().thenReturn(). On peut aussi vérifier les appels avec verify().
Quelle est la différence entre Surefire et Failsafe ?
Deux plugins Maven jumeaux. Surefire exécute les fichiers *Test.java pendant la phase test. Failsafe exécute les fichiers *IT.java pendant la phase integration-test → verify. La différence clé : Failsafe ne fait pas échouer immédiatement la build sur un test raté — il poursuit jusqu'à verify qui collecte les résultats. Cela permet d'exécuter des nettoyages post-test (arrêt de serveurs, etc.).
Comment JaCoCo mesure-t-il la couverture ?
JaCoCo attache un agent JVM au processus des tests. Cet agent instrumente le bytecode à la volée : il insère des compteurs à chaque ligne, branche, méthode, classe. Quand les tests s'exécutent, il enregistre les compteurs incrémentés. À la fin, il génère un rapport XML et HTML détaillant ce qui a été exécuté.
Que mesure SonarCloud exactement ?
Six métriques principales : Bugs (erreurs avérées), Vulnerabilities (failles sécurité OWASP/CWE), Security Hotspots (à revoir manuellement), Code Smells (dette technique), Coverage (consommée depuis JaCoCo), Duplications. Sonar applique 600+ règles classifiées Reliability / Maintainability / Security.
Qu'est-ce qu'un Quality Gate ?
C'est un ensemble de seuils que le code doit respecter pour passer. Exemple : "coverage >= 80% sur le nouveau code, 0 bug critique, 0 hotspot non revu". Le QG retourne PASSED ou FAILED. En CI/CD strict, un FAILED peut bloquer le merge de la PR.

🔐 Bloc 5 — Sécurité

Comment GitHub stocke-t-il les secrets ?
Chiffrement asymétrique : (1) côté navigateur, la valeur est chiffrée avec la clé publique du repo avant l'envoi, (2) GitHub stocke uniquement la version chiffrée, (3) au runtime, le runner déchiffre juste-à-temps. GitHub masque aussi automatiquement toute valeur secrète qui apparaîtrait dans les logs avec ***. C'est conforme au principe Zero Trust.
Que faire si un secret fuite ?
Rotation immédiate : (1) révoquer le token compromis, (2) en générer un nouveau, (3) mettre à jour le secret dans GitHub. D'abord rotation, ensuite enquête. Ne jamais penser "ce n'était que dans tel canal privé" — un secret exposé doit être considéré comme cassé.
À quoi sert Trivy ?
Trivy scanne les images Docker à la recherche de CVE connues : paquets OS (Alpine, Debian), dépendances Java/Node/Python, mauvaises configurations, secrets accidentellement intégrés. Complémentaire à SonarCloud (qui regarde le code source) : Trivy regarde l'image livrée. Format SARIF standard intégré à GitHub Security.
Qu'est-ce qu'une CVE ?
Common Vulnerabilities and Exposures. Identifiant standard d'une faille de sécurité publique, format CVE-YYYY-NNNNN. Maintenu par MITRE. Chaque CVE a un score CVSS de 0 à 10 qui mesure sa criticité. Exemple : CVE-2021-44228 (Log4Shell) score 10/10.

🚀 Bloc 6 — Pipeline & Workflow

Pourquoi le job quality ne tourne que sur main ?
SonarCloud a un quota limité sur le plan gratuit. Faire une analyse à chaque push sur develop, à chaque PR, exploserait le quota. Donc on limite à main via if: github.ref == 'refs/heads/main'. Sur les autres branches, on garde lint + test (rapides et gratuits).
Que se passe-t-il si un job échoue ?
Par défaut, GitHub Actions stoppe les jobs qui dépendent du job raté. Mais ici, le job notify a if: always(), donc il s'exécute quoi qu'il arrive — succès ou échec. C'est crucial pour la fail fast philosophy : on veut être notifié surtout en cas d'échec.
Comment fonctionne le cache Maven dans GitHub Actions ?
L'action actions/setup-java@v4 avec cache: maven sauvegarde le répertoire ~/.m2/repository entre les runs. La clé de cache est calculée à partir du hash de pom.xml. Si le POM ne change pas, le cache est réutilisé — réduisant la durée du job de ~60s à ~8s pour la phase de résolution des dépendances.
Quel est le rôle du fichier pom.xml ?
C'est le POM (Project Object Model) Maven. Il déclare : (1) les coordonnées du projet (groupId, artifactId, version), (2) les dépendances (Jakarta, Hibernate, etc.), (3) les plugins Maven (surefire, failsafe, jacoco, sonar, checkstyle, spotbugs), (4) le packaging (war). C'est l'équivalent de package.json pour Node ou requirements.txt pour Python.

💡 Bloc 7 — Choix techniques

Pourquoi Java 17 plutôt que Java 21 ?
Java 17 est la version LTS la plus largement adoptée en entreprise (release 2021, support jusqu'en 2029). Java 21 (release 2023) commence à se déployer mais Tomcat 10.1 ciblait initialement Java 17. Choix de stabilité plutôt que de bleeding edge.
Pourquoi Oracle plutôt que PostgreSQL ?
Choix historique du projet BiblioGest. Pour la CI, ce détail n'a aucun impact puisqu'on mocke les DAOs. Pour un nouveau projet on prendrait PostgreSQL : open source, plus léger, supporté nativement par Hibernate sans Oracle XE container.
Pourquoi avoir laissé Checkstyle/SpotBugs en mode informational ?
Le code applicatif existait avant l'ajout du lint — il contient 177 violations Checkstyle. Rendre le lint bloquant aurait nécessité un refactoring massif hors périmètre du sujet. On a donc choisi le mode informational : les violations sont rapportées en artifact, mais ne bloquent pas le pipeline. C'est une décision pragmatique qu'on documente clairement dans le rapport.
Pourquoi avoir implémenté 5 pipelines au lieu d'une seule ?
Le sujet du module demandait explicitement de "comparer les principes des moteurs CI/CD" et "adapter la même logique sur plusieurs outils pour comprendre les différences de syntaxe et de fonctionnement". Avoir GitHub Actions, GitLab, Jenkins, CircleCI et Travis CI prouve qu'on a compris les concepts communs (jobs, triggers, secrets) et les spécificités de chacun (Groovy vs YAML, stages vs DAG, etc.).

🐛 Bloc 8 — Problèmes & debugging

Quelles ont été les principales difficultés ?
Six difficultés majeures : (1) tests sans base de données → résolu avec Mockito + extraction de la logique pure, (2) bug pré-existant constructor package-private → constructeur public, (3) commentaires inline SQL ignorés par sqlplus → suppression des commentaires, (4) bloc env: dupliqué en YAML → fusionné, (5) version Trivy 0.24.0 retirée du marketplace → pin sur master, (6) port 8080 occupé sur le poste → remappé sur 8081.
Comment debugger une pipeline qui échoue ?
Méthodologie en 5 étapes : (1) lire le message d'erreur exact dans l'UI Actions, (2) identifier le step précis qui rate, (3) reproduire localement la même commande (mvn checkstyle:check), (4) si reproductible : fix local + push ; si non reproductible : différence d'environnement (variables, OS, versions), (5) ajouter echo dans la pipeline pour clarifier l'état.
Pourquoi le Invalid workflow file: env is already defined ?
YAML interdit deux clés identiques au même niveau. On avait défini env: deux fois dans le même step Slack. Quand le YAML est invalide, GitHub Actions refuse entièrement de parser le fichier — c'est pourquoi tous les jobs apparaissaient en "failure" sans même tourner. Fix : fusionner les deux blocs en un seul.

🏗️ Bloc 9 — Architecture

Comment scalez-vous le pipeline si l'équipe grossit ?
Plusieurs leviers : (1) self-hosted runners sur des machines plus puissantes, (2) parallélisation des tests via matrix strategy, (3) cache plus agressif (sccache pour C++, Turbo pour monorepos JS), (4) split en plusieurs workflows (CI rapide pour PR, CI complet la nuit), (5) déplacement des tests E2E en pipeline séparée déclenchée par cron.
Si vous deviez ajouter le déploiement automatique en prod, comment feriez-vous ?
Ajouter un 8ème job deploy conditionné à main qui : (1) authentifie sur le cluster Kubernetes (kubeconfig stocké en secret), (2) applique un manifest Helm/Kustomize, (3) attend la stabilité via kubectl rollout status, (4) lance un smoke test sur l'URL de prod, (5) rollback automatique en cas d'échec. On déclencherait via un tag git (v1.2.3) plutôt que push pour avoir un contrôle manuel.
Comment géreriez-vous plusieurs environnements (dev, staging, prod) ?
Utiliser les GitHub Environments : on définit dev, staging, prod, chacun avec ses propres secrets (DB_URL différentes, tokens différents). On peut ajouter des required reviewers avant déploiement en prod (4-eyes principle). Le workflow utilise alors environment: production pour cibler le bon set de secrets.

🎯 Bloc 10 — Vision stratégique

Quelle est la limite principale de votre pipeline actuelle ?
Trois limites : (1) pas de tests E2E réels (pas de stack complète démarrée), (2) pas de déploiement automatique en prod (pipeline arrêté à la publication d'image), (3) couverture de code faible (~8%) — nécessiterait du test sur les Servlets et DAOs avec Testcontainers.
Comment justifiez-vous l'investissement initial en CI/CD ?
Le ROI se calcule en 3 axes : (1) réduction des bugs en prod (coût ×100 vs CI), (2) gain de temps des développeurs (pas de tests manuels répétitifs), (3) amélioration du time-to-market. Le setup initial (1-2 semaines/dev) est rentabilisé en quelques mois sur un projet actif. Référence : étude DORA "Accelerate" — les équipes haute performance déploient 200× plus vite avec 7× moins d'échecs.
Quelles sont les évolutions futures envisagées ?
Court terme : passer en Continuous Deployment vers un cluster K8s, ajouter des tests E2E via Playwright, intégrer Renovate pour le bump auto des dépendances. Moyen terme : observabilité (Prometheus, Grafana, OpenTelemetry), feature flags (LaunchDarkly), GitOps via ArgoCD. Long terme : matrix builds multi-Java (17 + 21), tests de charge automatisés via k6 ou Gatling.
Quel est selon vous le rôle principal d'un ingénieur DevOps ?
Outiller les équipes pour qu'elles soient autonomes — pas faire les déploiements à leur place. Un bon DevOps construit des plateformes self-service (Internal Developer Platform), automatise les chemins répétitifs, encode les bonnes pratiques de sécurité et conformité dans les pipelines. Il évangélise la culture du "vous le construisez, vous le runnez" (Werner Vogels, Amazon).

🔍 Bloc 11 — Vocabulaire technique

Qu'est-ce que l'Infrastructure as Code ?
Décrire l'infrastructure (serveurs, réseaux, services) sous forme de fichiers texte versionnés, plutôt que via une UI cloud. Avantages : reproductibilité, revue de code, rollback, audit. Outils : Terraform, Pulumi, AWS CloudFormation, Ansible. Notre Dockerfile + docker-compose.yml sont des formes simples d'IaC.
Qu'est-ce que le shift-left security ?
Déplacer les contrôles de sécurité vers le début du cycle de vie logiciel — autrement dit dans la pipeline CI/CD plutôt qu'en audit annuel. Concrètement : SAST (SonarCloud), SCA (Dependabot, Snyk), container scan (Trivy), secret scanning (GitHub Advanced Security). Notre pipeline implémente shift-left avec lint + Sonar + Trivy.
Qu'est-ce qu'un artifact registry et pourquoi est-ce critique ?
Un registre stocke les artefacts construits par la CI : images Docker, paquets npm, JARs Maven, etc. C'est critique car : (1) il garantit la reproductibilité (même version = même artefact), (2) il découple build et déploiement (on peut redéployer une vieille version), (3) il centralise les CVE scans (Trivy lit depuis le registry).
Qu'est-ce que le GitOps ?
Paradigme où Git est la source de vérité unique pour l'infrastructure ET le déploiement. Un opérateur (ArgoCD, Flux) surveille un repo Git contenant les manifests Kubernetes et applique automatiquement les changements au cluster. Avantages : audit complet, rollback = git revert, accès limité au cluster (seul l'opérateur push).
Qu'est-ce qu'un service mesh ?
Couche d'infrastructure qui gère la communication service-à-service (load balancing, retry, circuit breaker, mTLS, observability) sans toucher au code applicatif. Implémentations : Istio, Linkerd, Consul Connect. Pas pertinent pour notre projet monolithique, mais essentiel pour les architectures microservices.
Qu'est-ce que la supply chain security ?
Sécurisation de toute la chaîne logistique du logiciel : dépendances OSS, images de base Docker, actions de CI/CD, registres. Risques majeurs : dependency confusion (npm), compromission de mainteneur, image base avec backdoor. Bonnes pratiques : pin sur SHA, SBOM (Software Bill of Materials), signature d'artefacts (Cosign), scan continu (Trivy, Snyk).
Que signifie le terme immutable infrastructure ?
Une infrastructure n'est jamais modifiée après son déploiement. Pour mettre à jour, on déploie une nouvelle version et on détruit l'ancienne — pas de ssh + apt-get upgrade. Avantages : prédictibilité, rollback simple, pas de drift de config. Les conteneurs Docker incarnent ce principe.
Pourquoi fail fast est-il important ?
Échouer au plus tôt évite de gâcher du temps et des ressources. Dans notre pipeline, lint tourne en premier (15s) — s'il y a un défaut de style, on le sait avant les 2 min de tests. La construction Docker (3 min) ne démarre que si tout le reste a passé. C'est l'optimisation Pareto : on attrape 80% des défauts dans les 20% premiers seconds.
Quelle est la différence entre monorepo et polyrepo ?
Monorepo : tout le code dans un seul repo Git (Google, Meta, Microsoft, Uber). Polyrepo : un repo par service/composant. Notre projet est polyrepo (un seul service donc trivialement). Monorepo facilite refactoring transverse et atomic commits, polyrepo facilite ownership et autonomie d'équipe.
